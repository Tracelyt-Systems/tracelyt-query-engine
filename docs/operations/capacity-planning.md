# Capacity Planning & Workload Sizing

This document outlines the architectural variables, workload dimensions, and future benchmarking methodologies required to accurately size `tracelyt-query-engine` deployments.

> **Important Notice:** No synthetic benchmarks, fake latency guarantees, or fictional queries-per-second (QPS) numbers are included in this document. Real capacity metrics must be established through empirical benchmarking against actual production workloads in future milestones.

---

## 1. Why User Counts Are Insufficient for Sizing

Sizing an observability query subsystem based simply on "number of registered users" or "organization count" is flawed because:
- **Autonomous Systems Generate Heavy Traffic:** Automated alerting systems (`tracelyt-alerting`) evaluate periodic queries every 10–60 seconds, 24/7, independent of human dashboard users.
- **Query Variance Spans Orders of Magnitude:** A single dashboard refresh may trigger 30 concurrent sub-queries spanning distinct metrics panels, while an analytical investigator query may scan hundreds of gigabytes of raw log data.
- **Cardinality Determines Memory Footprint:** Two queries requesting the same 1-hour time window will have vastly different resource costs if one queries a single low-cardinality counter and the other aggregates across 500,000 unique ephemeral container IDs.

---

## 2. Key Capacity Variables

A realistic capacity model must evaluate:

| Variable | Architectural Impact | Primary Resource Constrained |
|---|---|---|
| **Query Arrival Rate (QPS)** | Peak queries submitted per second across interactive and alerting workloads. | Coordinator CPU, thread pools, network sockets. |
| **Concurrent In-Flight Queries** | Total queries executing simultaneously against storage. | Admission queue capacity, JVM heap memory. |
| **Data Scanned per Query** | Total compressed and uncompressed bytes scanned from storage. | Storage node I/O, storage-to-coordinator network bandwidth. |
| **Result Payload Size** | Total data serialized into response JSON/Protobuf envelopes. | Coordinator JVM heap, garbage collection overhead. |
| **Time-Range Width** | Range requested (e.g., 5 minutes vs. 30 days). | Storage partition pruning effectiveness. |
| **Signal Type** | Metrics (numeric series) vs. Logs (unstructured text) vs. Traces (DAG spans). | Deserialization CPU, memory buffer allocation. |
| **Dimension Cardinality** | Number of unique series generated by `GROUP BY` clauses. | Hash table memory allocation, merge phase CPU. |
| **Underlying Storage Latency** | Time taken by storage engine to return filtered partitions. | Coordinator connection hold time. |

## 3. Workload Profiles

Deployments will encounter three distinct query workload profiles:

```text
1. Interactive Dashboard Queries:
   - High concurrency, low latency expectation (< 500ms), short time window (last 15m to 2h).
   - High cache potential for non-overlapping historical tiles.

2. Alert Evaluation Queries:
   - Predictable schedule, small time windows (e.g., 5m sliding window), strict SLA (< 5s).
   - Must be prioritized over ad-hoc user queries to prevent alert delays.

3. Deep Investigation / Ad-Hoc Analytics:
   - Low concurrency, broad time windows (7 to 30 days), regex filtering, large result sets.
   - Must be strictly isolated to prevent starving interactive dashboard queries.
```

## 4. Future Benchmarking Methodology

When query execution implementations are ready for capacity validation in subsequent roadmap phases, benchmarking must adhere to:
1. **Reproducible Test Environment:** Dedicated isolated hardware or cloud instances; no shared CPU or burstable instances.
2. **Realistic Telemetry Datasets:** Telemetry generated with realistic entropy, label cardinality, and time distributions (no repeated constant values that distort compression).
3. **Statistical Latency Distribution:** Report P50, P90, P99, and P99.9 latency curves, rather than misleading simple averages.
4. **Saturation & Recovery Testing:** Step-load testing to identify the exact inflection point where queues saturate, measuring how cleanly the service sheds load (`429`) and recovers when load normalizes.
